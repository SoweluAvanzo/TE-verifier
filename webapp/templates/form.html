Token Economy Verifier

Advanced (YAML editor) → Monte Carlo → Trajectory explorer →

Answer the questions on the left to describe your token economy. The verifier runs the six failure-mode checks and shows verdicts, critical values, and concrete redesign recommendations on the right. Each question links to the failure modes it feeds and the paper section that justifies it.

How to use this
  1. Either fill in the form section by section, or click an example below to pre-populate every field with a known token economy (Bitcoin, Ethereum, MakerDAO, Curve, Axie).
  2. Click Verify. The right pane shows a per-failure-mode verdict with the critical parameter value you'd need to clear, plus the structured-choice mechanisms that satisfy it.
  3. Tweak any field and click Verify again to see the verdict update — this is how you explore the design space.
  4. Use Download YAML at the bottom to save your spec, or Upload YAML to load one.

"I don't know" is a valid answer. When you leave a range field with a wide span (e.g. γ ∈ [0, 1]), the verifier searches across the whole range and tells you the critical value at which the verdict flips.

1 System identity

Name your token economy and pick the archetype that best fits its intent. The archetype shapes which failure modes apply most acutely.

Why we ask

Archetype drives sensible defaults and highlights the failure modes most relevant to your design. For example, a stablecoin's value-anchor question becomes decisive (FM3); a play-to-earn dual token immediately triggers FM1 + FM2 + FM3 + FM4 evaluation.

See docs/specification-flow.md Stage 1 for archetype routing semantics.

native_protocol_asset = Bitcoin, Ethereum. stablecoin = DAI, USDC. governance_utility_pair = MakerDAO, Curve. play_to_earn_dual = Axie, STEPN. community_reward = volunteer-reward systems.

2 Tokens (Roadmap Groups 1–3)

Add one or more tokens. Each token gets its own design fields (Group 1), mint mechanisms (Group 2), and burn mechanisms (Group 3). Mechanisms compose additively — see docs/proofs/composition.md.

Why we ask

Multi-mechanism mint and burn are common in real systems (initial allocation + ongoing rewards; demand-driven burn + rule-driven burn). The verifier sums them per Simulator.pdf §3.3 eq (7). For multi-token systems, see also the next stage (Inter-token relationships).

3 Inter-token relationships

Optional. Declare flows between tokens — e.g. "fees on DAI drive proportional MKR burn" or "burning AXS mints SLP". Independent flows have a fixed amount class; proportional flows scale with the source token's own emission.

Why we ask

Cross-token flows feed FM1 (oversupply) and FM3 (burn coverage) on the target token. Proportional coupling captures patterns like MakerDAO's MKR buyback-and-burn (proof: docs/proofs/coupled_flows.md).

4 Events (catalog)

Why we ask

Define every event that drives token mints, burns, or population changes here once. Mint / burn rules and condition predicates reference these events by id — no inline trigger definitions any more.

Each event captures (1) its kind — time_based / behavioral / physical_resource_flow / algorithmic / demand_driven / etc. — and (2) its frequency, an asymptotic class describing how many firings per period. For pure time-based events the frequency is implicitly 1 (leave it empty).

4.1 Non-tokenized assets

Why we ask

Goods, services, badges, NFTs that participate in the economy without being fungible tokens themselves. The ABM tracks per-asset inventory + cumulative creation / consumption; the verifier treats them as redemption sinks for FM3 burn-pathway feasibility.

Mark unique=true for NFTs (single spawn). Creation / consumption shapes mirror token mint / burn rules.

7 Agent types (Roadmap 5.5–5.6)

Add one or more agent types. Their fractions must sum to ~1.0. Holding times feed τ̄ (FM2); roles feed φ (FM4).

Population events (mid-simulation spawn / despawn / utility shift)

Schedule changes to the agent population that fire at a specific period during simulation. Use this for stress tests like "what if 30 % of consumers leave at period 50" or "what if the staking yield doubles at period 100". Leave empty for static populations.

Verdict

The right pane will show the per-failure-mode verdict here once you click Verify. For each failure mode, you'll see:

  • Status — pass, fail, pass-as-intended, inconclusive, or N/A.
  • Critical value — the threshold parameter you'd need to clear.
  • Recommendation — a concrete redesign instruction with mechanism options ranked safe / partially safe / unsafe.
  • Counterexample — a concrete failing assignment with binding-constraint indicator.
